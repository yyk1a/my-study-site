整理自 2026-09-19 ~ 09-20 的一次真实排错过程 · 以项目 ~/ws63/sparklink-book 为实例 · 目标命令：./build.py menuconfig ws63-liteos-app

一、你的环境背景

项值
开发方式Windows 上 VSCode，远程连 WSL
子系统WSL Ubuntu
Python 版本3.14（系统自带，受 PEP 668 保护）
项目路径~/ws63/sparklink-book
要跑的命令./build.py menuconfig ws63-liteos-app

二、第一个坑：externally-managed-environment

现象：sudo pip install xxx 报

error: externally-managed-environment
This environment is externally managed

原因：Python 3.11 / Ubuntu 23.04 起启用 PEP 668，系统自带 Python 被标记为"由 apt 托管"，禁止 pip 往系统目录写包，避免破坏系统工具依赖。Python 3.14 触发了它。这是保护机制，不是故障。

核心结论：书的老写法 sudo pip install xxx 在旧 Ubuntu 能用，在新版系统已失效，要改用下面的正确渠道。

三、判断：这个包该走 apt 还是 pip？

类型例子安装方式
系统级构建工具（命令行程序）cmake、gcc、gitsudo apt install
Python 命令行工具（独立 app）kconfiglib（menuconfig/guiconfig 命令）pipx install
Python 库（代码里 import 用）kconfiglib（被 build.py import）、pycparservenv + pip install
apt 源里没有的 Python 包kconfiglib、pycparserapt 查不到 → 走 pip/pipx/venv

项目里的对应关系：

  • cmake → sudo apt install cmake（apt 有，系统级编译工具，已装好 ✅）
  • kconfiglib → 既是命令行工具又是 build.py 要 import 的库 → 必须用 venv（见第五节）

四、工具选型速查（PEP 668 之后）

需求命令说明
装系统程序sudo apt install 包系统级，最稳
装 Python 命令行 apppipx install 包每个工具独立小环境，命令进 PATH
装 Python 库（供 import）python3 -m venv .venv + source .venv/bin/activate + pip install 包build.py 这类脚本必须走这个
应急（不推荐）pip install 包 --break-system-packages绕过保护，有风险，别养成习惯

书里出现的 sudo pip install xxx，在新系统上统一翻译为：

· 查得到 apt 包 → sudo apt install xxx
· 查不到 → 若是命令行工具用 pipx install xxx；若是库（会被 import）必须用 venv

五、正确操作流程（完整版）

第 0 步：确认终端是 WSL，不是 PowerShell

  • ❌ 错：PS C:\Users\yyk1a\ws63\sparklink-book>
  • ✅ 对：yyk1a@LAPTOP-xxx:~/ws63/sparklink-book$（带 $ 结尾、Linux 路径）
  • 切换：终端面板 + 右边的 v 下拉 → 选 Ubuntu (WSL)；或直接在 PowerShell 敲 wsl

第 1 步：进项目目录

cd ~/ws63/sparklink-book

第 2 步：建 venv（独立 Python 环境）

python3 -m venv .venv
source .venv/bin/activate      # 激活后提示符前面出现 (.venv)

venv 隔离的是"Python 运行环境 + 装的库"，代码文件原封不动，只是多了个 .venv/ 文件夹。项目 .gitignore 里加 .venv/。

第 3 步：在 venv 里装需要的 Python 库

pip install setuptools        # ⚠️ 关键：Python 3.12+ 已删除标准库 distutils，build.py 用的 pkg_resources 依赖它
pip install kconfiglib        # build.py 需要 import kconfiglib
pip install pycparser         # 书里列的，按需（通常会被别的包自动带）

为什么必须装 setuptools：Python 3.12 起官方删除了标准库 distutils，而新建的 venv 默认不预装 setuptools。书里的 build.py 通过 pkg_resources（属于 setuptools）调用 distutils，缺了就报 ModuleNotFoundError: No module named 'distutils'。新版 setuptools 自带 distutils 兼容实现，装上即补齐。

之后若 build.py 再报 ModuleNotFoundError: No module named 'xxx'，保持 (.venv) 激活，继续 pip install xxx（常客还有 pyyaml 等）。老 SDK 在新 Python 上跑，基本就是"缺什么补什么"。

第 4 步：跑 menuconfig

./build.py menuconfig ws63-liteos-app

终端清屏，出现蓝黄边框的 Kconfig 配置界面即成功。

以后每次开新终端

cd ~/ws63/sparklink-book
source .venv/bin/activate     # 看到 (.venv) 才算就绪
./build.py menuconfig ws63-liteos-app

六、menuconfig 界面按键（纯键盘，鼠标无效）

按键作用
↑ ↓上下移动高亮条

Esc 连按两次返回上一级

改完记得 S 保存 再 Q 退出，否则不生效。

七、报错 → 对策 速查表

报错现象原因对策
externally-managed-environmentpip 直装系统 Python 被拦改用 apt / pipx / venv
Unable to locate package xxx（apt）apt 源无此包查不到就走 pip/pipx/venv
ModuleNotFoundError: No module named 'kconfiglib'pipx 装的只能命令行用、import 不到在 venv 里 pip install kconfiglib 再跑 build.py
ModuleNotFoundError: No module named 'distutils'Python 3.12+ 删了标准库 distutils，venv 又没预装 setuptools在 venv 里 pip install setuptools 再跑 build.py
终端出现 >>> 或 >> 提示符、无 menuconfig在 PowerShell 里跑了脚本切到 WSL Ubuntu 终端重来

八、一句话总结

系统工具（cmake）走 apt；Python 命令行工具走 pipx；被 build.py import 的库（kconfiglib）必须放进 venv；一切命令在 WSL Ubuntu 终端里跑，别在 PowerShell。

WS63 编译到烧录 · 实操手册

2026-09-22 整理 · 适用场景：写好/改好某个 demo 的代码，从「编译」一路搞到「板子跑起来」 · 活工程在 WSL：~/ws63/sparklink-book

0. 一句话心智模型（先记住）

menuconfig 决定「编谁」 →  你改的 main.c 决定「干什么」
→  编译打包成固件  →  烧录装进板子

同一章的 demo 是单选：你不进 menuconfig 切换，编译出来的永远是默认那个（hello world）。这是最容易踩的坑之一。

⚠️ 关联的第二个大坑（已确诊）：menuconfig 切了 demo 之后，直接增量编译往往还是编出旧的那个。因为旧的编译产物还躺在缓存里，CMake 没重新评估「该把哪个文件夹编进固件」。所以切完 demo 必须 ./build.py -c 清理后再编译（详见第 3 节）。

1. 每次动手前的固定前置（新终端都要做）

你要做打开 VSCode → 连 WSL（左下角显示 WSL: Ubuntu）→ 打开文件夹 /home/yyk1a/ws63/sparklink-book。

你要做在 VSCode 集成终端（Ctrl + `）里，每开一次新终端先激活环境（看到 (.venv) 才算就绪）：

source .venv/bin/activate

⚠️ 路径陷阱：venv 在 ~/ws63/sparklink-book/.venv，不是 ~/ws63。在 ~/ws63 下激活会报 No such file。先 cd ~/ws63/sparklink-book。

2. 切换你要编的 demo（换实验必做，否则白编）

你要做终端执行

./build.py menuconfig ws63-liteos-app

终端变成蓝黄边框菜单后：

  • ↓ 移到 Application → 回车 → ch2 samples
  • ↑↓ 移到你要的 demo（例：Support LED Demo.）
  • 按 空格 选中（单选：hello world 的勾会自动消失）
  • S 保存 → Q 退出

✅ 这一步写进 .config，决定编译时把哪个文件夹加进固件。

如果一直做同一个 demo、且当初已勾过，可跳过本步。

⚠️ 光做 menuconfig 还不够：LED 菜单切对了、编译也跑完了，板子却还是 hello world。根因是增量编译没刷新构建图——CMake 重新生成了配置头文件、重新打包，却没重新决定「把哪个 demo 编进固件」，hello world 的旧产物原封不动留在库里。所以切完 demo，必须紧跟第 3 节的 -c 清理，否则白切。

3. 编译（一条命令 —— 但切过 demo 时要先清理）

你要做

./build.py -j1 ws63-liteos-app
  • 编译到 [100%] 即成功，最后会打印固件路径，通常在：output/ws63-liteos-app/firmware/bin/ 下的 .fwpkg / .bin
  • 中途若报 ModuleNotFoundError: No module named 'xxx'：保持 (.venv) 激活，pip install xxx 再重编。
  • 黄色 SyntaxWarning 无视。

⚠️ 切换 demo 后必须 -c 清理重编（这是 LED 不生效的根因）：

./build.py -c ws63-liteos-app     # 清掉整个 output 下的旧构建缓存
./build.py -j1 ws63-liteos-app    # 全量重编（会花十几分钟，正常）

第一次全新构建会自动全量配置，所以之前没遇到；但改过 menuconfig 之后是增量编译，CMake 不会重新把目标 demo 加进编译图。不清缓存 → 编出来的还是旧 demo（hello world）。所以「换实验」的标准流程是 menuconfig 切换 → -c 清理 → -j1 编译 三步缺一不可。

4. 烧录（在 Windows 侧做，板子插在 Windows 上）

插板子Type-C 怼到底听到/感到「咔哒」，别只看红灯亮就以为到位（红灯亮但没插紧，会导致设备识别失败）。

确认 COM 口设备管理器 → 「端口 (COM 和 LPT)」出现 USB-SERIAL CH340 (COMx)，记下 COM 号。

选固件用烧录工具时，文件选 WSL 里的产物，直接在工具的文件框输：

\\wsl$\Ubuntu\home\yyk1a\ws63\sparklink-book\output\ws63-liteos-app\firmware\bin\...

（不用把固件拷到 Windows）

烧录选对应 COM → 点烧录 → 按工具提示（通常按板子 RESET 键或重新插拔）开始下载，进度条走完即成功。

⚠️ 必须烧本次新编译的固件，不能烧旧的 bin —— 改了 demo 不重编、只重烧旧文件，板子还是跑老程序。

5. 完整操作序列（照抄版）

cd ~/ws63/sparklink-book          # 进工程（不是 ~/ws63）
source .venv/bin/activate         # 激活，看到 (.venv)
./build.py menuconfig ws63-liteos-app   # 切 demo：空格选中 LED Demo，S 保存 Q 退出
./build.py -j1 ws63-liteos-app    # 编译

然后 → Windows 烧录工具选 \\wsl$\... 下新固件 + 对应 COM 口 + 按 RESET。

6. 踩过的坑（都是操作层面）

现象原因（操作）正确做法
激活 venv 报 No such file在 ~/ws63 而不是 ~/ws63/sparklink-book先 cd 进工程目录再激活
烧完还是 hello world没进 menuconfig 把单选切到 LED Demo编译前先 menuconfig 空格选中目标 demo

7. 关于那两份目录（防迷路）

  • 活工程（编译用的）：WSL ~/ws63/sparklink-book，含 build.py、.venv。
  • Windows 旧镜像：已改名 C:\Users\yyk1a\ws63\_backup_sparklink-book_win，只用来看代码、不要编译它，免得「A 份改了、B 份编了」。
  • 改代码、编译、开终端一律用 WSL 这份；烧录用 \\wsl$ 路径取它的产物。
